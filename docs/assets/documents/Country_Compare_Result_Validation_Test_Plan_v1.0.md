# Country Compare — Result Validation & End-to-End Test Plan

*Version 1.0 • Target application release 1.0.1 • Branch: main*

*Prepared 20 August 2026*

> **Purpose**
> Establish independent confidence that Country Compare loads correct source data, calculates comparison/scoring/forecast results correctly, preserves those results through the API/client layers, and displays/exports the same trustworthy values in the deployed Streamlit UI.

# 2. Purpose and objectives

- Validate that source/canonical data used by the application is correct, traceable, structurally valid, and semantically configured correctly.

- Validate comparison, normalization, ranking, weighted scoring, deterministic forecasting, backtesting, predicted comparisons, and LLM bounded-adjustment behavior using independent oracles or invariants.

- Validate that service/API/client serialization does not change values, rankings, warnings, diagnostics, or metadata.

- Validate that the deployed Streamlit UI shows and exports the same results returned by the trusted backend path.

- Define which checks run automatically in pull requests, container integration, post-deployment, scheduled quality jobs, and which checks intentionally remain human review gates.

# 3. System under test and scope

In scope for release 1.0.1:

- Canonical release dataset and World Bank-backed metric provenance/metadata.

- Overview metadata shown in the UI.

- Compare: Single Metric, Multi Metric, Weighted Score.

- Prediction: deterministic single/multi-country forecasting, backtesting, predicted single-metric, predicted multi-metric, and predicted profile comparisons.

- Optional llm_forecast service integration, readiness/capability gating, bounded adjustment, fallback, privacy, and UI exposure.

- FastAPI metadata/comparison/prediction routes, result-envelope serialization, API limits/security, and local/HTTP client parity.

- Streamlit HTTP-backed production mode, warnings/diagnostics, charts as data transformations, and CSV/JSON/Markdown exports.

- Render post-deployment verification and scheduled source/forecast-quality checks.

Out of scope for this document:

- The not-yet-deployed Kafka/Postgres/MinIO data-update subsystem; it should receive a separate operational test plan when promoted into the production path.

- Pixel-perfect screenshot regression as the primary way to prove numeric correctness. Visual review is used only for readability/usability; values are validated from structured tables/exports/API responses.

- Proving that an LLM forecast is objectively “true.” Live LLM checks validate invariants, bounds, failure behavior, and reasonableness; forecast quality is evaluated statistically via backtesting.

# 4. Test strategy

| **Validation layer** | **Question** | **Primary evidence** |
| --- | --- | --- |
| 1. Source truth | Is the loaded source observation correct? | Source-verified World Bank goldens + release parquet checks |
| 2. Semantic correctness | Is the metric interpreted correctly? | Indicator mapping, unit/scale review, higher_is_better decisions |
| 3. Calculation oracle | Is the computation mathematically correct? | Tiny synthetic fixtures with independently calculated expected results |
| 4. API/client parity | Did transport/serialization change meaning? | Service/local-client vs HTTP/API equality |
| 5. UI parity | Is the same result shown/exported to the user? | Browser E2E + structured table/export equality |
| 6. Forecast/LLM quality | Are forecasts safe and useful within contract? | Deterministic oracles, backtests, LLM bounds/fallbacks, scheduled scorecard |

**Core rule:** expected values for result-validation tests must not be generated by the same production function being tested.

# 6. Test data and oracle design

- Oracle dataset: add a tiny synthetic long-format fixture under tests/validation/fixtures. Include at least three countries, both higher/lower-is-better metrics, a tie metric, missing observations, and a clean time series such as 10/20/30/40 for forecast math.

- Expected comparison/scoring/forecast/backtest outputs: store hand-calculated or separately calculated values in YAML/JSON. Production normalization/scoring/forecast functions must never be called to create the expected side of the same test.

- Release source-truth fixture: maintain 2-3 independently verified World Bank observations per metric, including indicator code, country, year, expected value, tolerance, verification date, and review_status=verified.

- Post-deploy reference cases: use a frozen request set and compare deployed API/UI results with the same release oracle dataset/checksum. If live source data changes, create/review a new release fixture rather than silently changing expected values.

- LLM data: use mocked deterministic provider outputs for unit tests; live-provider checks use structural/bounded invariants and a small manual reasonableness sample, not exact output equality.

# 7. Numeric comparison and tolerance policy

- Synthetic deterministic oracles: exact equality where mathematically exact; otherwise use a tight floating-point tolerance (recommended 1e-9 or stricter where stable).

- Source values: use metric-specific absolute and/or percentage tolerances recorded in the verified golden fixture; do not apply one broad global tolerance.

- API versus export/UI raw values: expect exact semantic equality of serialized raw values. Display rounding is allowed only in presentation text; exported/raw table values must remain faithful to the backend result.

- LLM forecasts: do not use exact-value assertions for live provider output. Enforce finite values, expected years/count, identity, configured adjustment bound, and safe deterministic fallback.

# 8. Entry and exit criteria

Entry criteria for release validation:

- Release candidate commit identified and built from the intended main revision.

- Release parquet/config artifacts generated and validate-config/validate-data pass.

- Automated unit/integration/static checks are green before manual release QA begins.

- Render environment variables/secrets are configured for the intended deployment topology.

Exit criteria / release gate:

- All P0 automated cases pass in every stage where they apply.

- No unresolved P0 defect and no unresolved P1 defect that can produce wrong displayed values, ranking, forecast, or unsafe secret disclosure.

- All authoritative release goldens are source-verified; metric direction decisions are approved.

- Post-deploy API and UI reference smoke pack passes against Render.

- If LLM is enabled, capability/bounds/fallback/privacy checks pass and the manual live reasonableness sample is accepted.

- Manual UI readability/usability check is accepted for the release browser target.

# 12. Defect classification and evidence

| **Severity** | **Definition / examples** |
| --- | --- |
| Critical | Wrong source/value mapping broadly corrupts results; secret exposure; unsafe public LLM configuration; deployed UI connected to wrong backend/dataset. |
| High | Incorrect normalization/rank/score/forecast/backtest result; UI/API value mismatch; missing fallback warning that materially misleads the user. |
| Medium | Non-blocking metadata mismatch, partial diagnostic loss, export formatting issue that does not change values, significant usability problem. |
| Low | Cosmetic/documentation issue with no effect on interpretation or correctness. |

- Automated failure evidence should retain request payload, expected/actual structured values, dataset checksum/version, application version/commit, and relevant request ID.

- UI E2E failures should retain browser screenshot plus downloaded export/API response; screenshots are evidence of presentation state, not the numeric oracle.

- Source-truth discrepancies must record the exact source indicator/country/year and whether the external source was revised. Do not auto-update expected values.

- LLM live failures should retain sanitized baseline/output deltas and diagnostics only; never attach secrets or raw confidential prompts.

# 13. Implementation order

1. Phase 1 — Release data gate: wire COUNTRY_COMPARE_DATA_CORRECTNESS_PATH into CI; verify and enforce authoritative release goldens; complete higher_is_better review.

1. Phase 2 — Independent calculation oracles: normalization/ranking, weighted scoring, deterministic forecast methods, and backtest metrics.

1. Phase 3 — API/client parity: execute the same oracle requests through service/local client and FastAPI/HTTP client.

1. Phase 4 — Browser E2E: add Playwright (or equivalent) cases that compare UI tables/exports to API reference results. Prefer structured exports/table data over screenshot assertions.

1. Phase 5 — Post-deploy gate: add a GitHub Actions job after Render deployment that runs the P0 API + browser reference pack and optional LLM invariants.

1. Phase 6 — Scheduled quality: source drift/freshness and forecast backtest scorecard.
